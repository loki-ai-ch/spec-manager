# 方法论文档可信度与可执行性加固 — 需求文档

## 背景

当前方法论文档已经形成完整的 L1 → L2 → L3 → Agent Task 主线，并新增了约束闭环、分层验收、失败上下文和外部实践等说明。但审核发现，文档中至少有 8 类表述与实际能力或规则语义不完全一致：

- 将警告、记录能力和人工操作描述为硬门禁、自动重试或确定性调度。
- 将所有 Spec 层级合并成同一状态机，掩盖 L1/L2 与 L3 的生命周期差异。
- 将代码调查规则误写为所有代码修改必须绑定 Agent Task。
- 最低审计合规基线遗漏实际已包含的规则。
- L3 与 Task 的产物定位混淆。
- 外部实践使用“验证”结论，但缺少可追溯证据。
- “真实环境可用”被定义为闭环终点，却没有说明当前系统是否强制该终点。
- 规范性契约、运行机制和设计理念混排，读者难以区分“系统保证”“流程要求”和“设计目标”。

这些问题会使使用者高估系统保证强度，或按错误状态机推进工作。若不处理，方法论文档会从流程入口变成新的语义漂移来源。

## 问题归类

| 类别 | 问题描述 | 优先级 | 证据来源 |
|---|---|---|---|
| 能力真实性 | 自动重试、确定性执行、真实环境验收等表述强于当前实际保证 | P1 | 文档审核与实现对照 |
| 规则一致性 | 状态机、R8、审计基线等表述与规则或实现不一致 | P1 | 文档审核与规则对照 |
| 可执行性 | 硬门禁、warning、人工审核和目标能力未明确分级 | P1 | 文档审核 |
| 信息架构 | 规范、机制、理念重复并混排 | P2 | 文档结构审核 |
| 证据可信度 | 外部实践结论缺少来源和实验边界 | P2 | 文档审核 |

## 用户故事

### Must have

- As a 方法论使用者, I want 明确知道哪些要求由系统强制、哪些只是 warning 或人工审核, so that 我不会误判流程保证。
- As a 项目维护者, I want 方法论文档与当前状态机、规则和审计基线一致, so that 文档不会指导 Agent 执行错误流程。
- As a Agent 使用者, I want 文档准确描述失败上下文与重试能力的边界, so that 我不会把辅助提示误认为自动调度。
- As a 审核者, I want 外部案例结论具有来源或被明确标记为启发, so that 方法论结论可追溯。

### Should have

- As a 新使用者, I want 按规范性契约、运行机制、设计理念阅读文档, so that 我能快速定位必须遵守的部分。
- As a 规则维护者, I want 关键事实具备一致性检查, so that 后续改动不容易重新引入语义漂移。

### Could have

- As a 方法论维护者, I want 文档区分当前能力与目标能力, so that 后续增强可以在不夸大现状的前提下演进。

## 功能目标

| 能力 | 现状(量化) | 目标(量化) |
|---|---|---|
| 已知语义失真 | 审核发现至少 8 类 | 已识别问题全部消除 |
| 门禁分级 | 无统一分类表 | 关键验收项全部标注 hard gate、warning、人工审核或目标能力 |
| 状态机描述 | 1 个统一状态图 | L1/L2、L3、Task 分别描述 |
| 外部证据 | 1 个无来源强结论 | 有可追溯来源，或降级为明确的实践启发 |
| 文档结构 | 规范、机制、理念混排 | 核心内容按职责分区，重复表述减少 |

## 验收标准

1. **AC-1**: **Given** 使用者阅读方法论中的验收与规则说明, **When** 判断某项约束是否由系统强制, **Then** 文档 **SHALL** 明确区分硬门禁、warning、人工审核和目标能力。
2. **AC-2**: **Given** 使用者查看生命周期说明, **When** 分别检查 L1/L2、L3 和 Task, **Then** 文档 **SHALL** 给出与当前系统一致的独立状态流。
3. **AC-3**: **Given** 使用者查看失败处理与重试说明, **When** 对照当前能力边界, **Then** 文档 **SHALL NOT** 将失败上下文提示描述成自动重试或确定性执行。
4. **AC-4**: **Given** 使用者查看规则摘要与审计基线, **When** 对照当前规则定义, **Then** 文档 **SHALL** 正确描述 R8、quick 例外和最低合规基线。
5. **AC-5**: **Given** 使用者查看 L3 与 Task 的定位, **When** 判断设计态和执行态产物, **Then** 文档 **SHALL** 将 L3 描述为实施规格或契约，并将 Task 描述为执行记录。
6. **AC-6**: **Given** 文档引用外部实践, **When** 该实践无法提供可追溯来源和实验边界, **Then** 文档 **SHALL** 将其描述为实践启发而非方法论验证。
7. **AC-7**: **Given** 文档优化完成, **When** 运行文档一致性检查, **Then** 已识别的错误强表述和过时基线 **SHALL NOT** 再出现。
8. **AC-8**: **Given** 本次优化仅针对方法论表达, **When** 检查项目行为, **Then** 运行时状态转换、Task 完成条件和 CLI 行为 **SHALL NOT** 发生改变。

## 度量指标

| 指标 | 基线 | 目标 | 测量方式 |
|---|---|---|---|
| 审核发现问题关闭率 | 0/8 类 | 8/8 类 | 逐项复核审核清单 |
| 关键规则一致性 | 存在已知偏差 | 已识别偏差为 0 | 与规则定义和当前行为对照 |
| 强结论可追溯率 | 待测量 | 100% | 检查强结论是否有来源或能力依据 |
| 文档回归检查 | 无专项检查 | 覆盖关键错误表述 | 自动化文本一致性检查 |

## 范围边界

- **做**:
  - 修正方法论文档中与当前规则、状态机和实际能力不一致的表述。
  - 增加门禁能力分级和当前能力边界说明。
  - 调整文档结构，减少规范、机制和理念之间的混淆与重复。
  - 为关键语义增加回归检查。
- **不做**:
  - 不改变运行时状态机、Task 完成条件、verification 模型或 CLI 行为。
  - 不实现自动重试、自动调度、AC 覆盖率强制或真实环境强制验收。
  - 不重写其他产品说明文档中与本次审核无关的内容。
- **推迟**:
  - 将真实环境验收和关键 AC 覆盖升级为系统硬门禁。
  - 实现自动 retry 状态机和调度器。

## 设计原则

1. **事实优先于宣传** — 文档只能声明当前可证明的系统保证。违反判断：文档使用“必然”“自动”“强制”等词，但没有对应门禁或调度实现。
2. **门禁必须分级** — 每项流程要求应能判断其执行主体和强制程度。违反判断：读者无法判断失败后是否阻止状态推进。
3. **状态按对象描述** — 不用单一状态图概括不同生命周期对象。违反判断：状态图包含某对象永远不会经历的正常状态。
4. **证据可追溯** — 强结论必须能追溯到系统行为、规则定义或公开来源。违反判断：结论无法复核来源或适用边界。
5. **当前能力与目标能力分离** — 未来方向不能写成当前保证。违反判断：目标能力出现在现行门禁或验收描述中。

## 风险与依赖

| 风险/依赖 | 影响 | 缓解措施 |
|---|---|---|
| 方法论文档当前已有未提交修改 | 优化时可能覆盖用户已有内容 | 保留现有改动并基于当前版本增量修改 |
