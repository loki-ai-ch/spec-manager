# 核心架构分层重构 — 需求文档

## 背景

当前项目已经具备稳定质量基线：代码走读时统计到生产 TypeScript 约 8,113 行，自动化测试基线为 481/481 通过，项目诊断结果为 ok。此前的架构加固已经覆盖流程绕过、路径安全、完整 rename、完整性扫描和兼容迁移，说明现阶段主要风险不再是明显缺陷，而是核心能力继续增长时的结构承载能力。

代码走读发现，当前核心逻辑存在 3 类可量化集中点：

- 任务完成链路承载至少 7 类职责：事务快照、任务状态流转、步骤验收、验证命令执行、规则验证、规格级联、决策门禁与审计记录。
- 规格读写链路同时承担 markdown/frontmatter 仓储、状态流转、父子层级约束、内容摘要约束、关系目标校验和审计记录。
- 项目视图、完整性诊断、生命周期判断等只读能力都需要读取 specs、tasks、decisions、incidents、changes，但目前缺少统一的项目快照抽象，规则增加后容易产生重复扫描和判断口径分叉。

不处理这些问题的直接后果是：后续新增验证闭环、审计合规、归档增强等能力时，会继续把规则叠加到既有枢纽函数中；每次修改都需要同时理解领域规则、文件读写、事务、审计和 CLI 输出，回归风险会随功能数量非线性上升。

## 问题归类

| 类别 | 问题描述 | 优先级 | 证据来源 |
|---|---|---|---|
| 用例职责集中 | 任务完成链路在单一用例中串联多类业务门禁和副作用，新增规则时缺少独立扩展点 | P1 | 代码走读：任务完成链路职责枚举 |
| 仓储与规则混合 | 规格读写能力同时处理文件 I/O、领域状态、规则审计，导致底层读写难以作为稳定基础复用 | P1 | 代码走读：规格创建与更新链路职责枚举 |
| 只读模型重复构建 | 多个诊断和展示能力各自读取并组合项目对象，缺少统一快照与索引 | P2 | 代码走读：视图、完整性、生命周期能力重复读取对象 |
| 变更归档流程复杂 | 变更归档同时覆盖解析、预检、应用、引用迁移、回滚和归档移动，后续增强 dry-run 或报告会增加复杂度 | P2 | 代码走读：归档链路职责枚举 |

## 用户故事

### Must have

- As a 维护者, I want 核心用例的业务门禁可以独立理解和测试, so that 新增流程规则时不需要同时修改多个无关副作用。
- As a 维护者, I want 仓储读写能力与领域规则分离, so that 文件格式和业务约束可以分别演进。
- As a 维护者, I want 项目级只读判断共享同一份快照和索引, so that doctor、flow、integrity 等输出基于一致数据口径。
- As a 使用 CLI 的开发者, I want 重构后既有命令行为保持兼容, so that 当前项目流程不会因内部架构变化中断。

### Should have

- As a 维护者, I want 变更归档先形成可解释的计划再执行, so that 归档失败、回滚和报告更容易定位。
- As a 维护者, I want 关键门禁以命名能力表达, so that 后续规格可以直接引用这些能力而不是复述流程细节。

### Could have

- As a 维护者, I want 重构后的只读快照可服务性能测量, so that 未来大型仓库可以进一步优化扫描成本。

## 功能目标

| 能力 | 现状(量化) | 目标(量化) |
|---|---|---|
| 任务完成链路可维护性 | 单一链路承载至少 7 类职责 | 每类门禁或副作用均有独立命名边界，任务完成编排只表达顺序与结果聚合 |
| 规格读写边界 | 仓储读写与至少 5 类领域规则混合 | 仓储能力只负责 markdown/frontmatter 持久化，领域规则由领域服务调用 |
| 项目只读判断口径 | 至少 3 类能力各自组合项目对象 | doctor、flow、integrity、lifecycle 可共享项目快照或等价只读模型 |
| 行为兼容 | 当前自动化测试 481/481 通过，项目诊断 ok | 重构后自动化测试仍为 481/481 通过或新增测试全部通过，项目诊断仍为 ok |

## 验收标准

1. **AC-1**: **Given** 当前项目存在稳定测试基线, **When** 架构重构完成, **Then** 既有自动化测试 **SHALL** 全部通过，且新增测试不得降低既有覆盖语义。
2. **AC-2**: **Given** 任务完成链路需要执行多个门禁, **When** 维护者阅读重构后的设计, **Then** 每类门禁 **SHALL** 能以独立命名能力定位，并能单独描述输入、输出和失败原因。
3. **AC-3**: **Given** 规格文件需要被创建、读取、更新, **When** 维护者查看仓储层职责, **Then** 仓储层 **SHALL** 不承担用户审批、状态授权、内容摘要或审计命中的业务判断。
4. **AC-4**: **Given** doctor、flow、integrity 或 lifecycle 需要读取项目对象, **When** 它们在同一项目状态下运行, **Then** 它们 **MUST** 基于一致的 specs、tasks、decisions、incidents、changes 视图作判断。
5. **AC-5**: **Given** 用户仍使用当前 CLI 工作流, **When** 内部架构重构完成, **Then** 用户可见命令语义、状态流转约束和项目诊断结果 **SHALL** 保持兼容。
6. **AC-6**: **Given** 后续需要增强变更归档, **When** 查看归档相关设计, **Then** 解析、预检、应用、引用迁移、回滚和结果报告 **SHOULD** 有清晰边界。

| 指标 | 基线 | 目标 | 测量方式 |
|---|---|---|---|
| 自动化测试通过率 | 481/481 通过 | 100% 通过 | 项目测试结果 |
| 项目诊断状态 | ok | ok | 项目诊断结果 |
| 任务完成链路职责集中度 | 至少 7 类职责在同一链路内直接交织 | 编排层只保留顺序、事务边界和结果聚合；门禁逻辑独立命名 | 代码审查与验收记录 |
| 仓储层规则混入数量 | 规格仓储链路混入至少 5 类业务规则 | 仓储层不直接触发审批、状态授权、审计规则 | 代码审查与验收记录 |
| 项目只读快照复用范围 | 待测量 | doctor、flow、integrity、lifecycle 至少 3 类能力复用统一只读模型 | 验收记录 |

## 范围边界

- **做**:
  - 梳理核心领域对象、仓储读写、业务门禁、用例编排的分层边界。
  - 将任务完成链路中的门禁与副作用拆成可独立验证的能力。
  - 将规格读写与规格业务规则解耦。
  - 为项目级只读判断建立统一快照或等价索引模型。
  - 保持现有用户工作流和命令语义兼容。
- **不做**(显式排除,至少 2 条):
  - 不改变现有 spec、task、decision、change 的存储格式。
  - 不重写 CLI 交互文案和命令体系。
  - 不引入数据库、服务端或网络依赖。
  - 不做面向大型仓库的性能专项优化。
- **推迟**(后续版本考虑):
  - 归档 dry-run 的结构化报告增强。
  - 大型仓库扫描性能基准与缓存策略。
  - 第三方插件式规则注册机制。

## 设计原则

1. **行为兼容优先** — 内部重构不得改变用户已依赖的流程约束和命令语义。违反判断: 既有测试或项目诊断在无业务变更情况下失败。
2. **仓储无业务判断** — 文件读写能力只负责安全、解析、序列化和原子写入。违反判断: 仓储层直接决定审批、状态授权、审计命中或用户流程。
3. **门禁显式命名** — 每个完成门禁都应有可引用的能力名、输入、输出和失败原因。违反判断: 只能通过阅读完整编排流程才能知道某条门禁存在。
4. **只读模型单一口径** — 同一轮诊断或展示中的项目对象关系应来自同一份快照或等价索引。违反判断: 不同只读能力各自重新组合对象并可能产生判断差异。
5. **小步可回滚** — 重构应按可独立验证的边界分阶段完成。违反判断: 单次实施同时改变多个核心用例且无法单独验证。

## 风险与依赖

| 风险/依赖 | 影响 | 缓解措施 |
|---|---|---|
| 重构触碰核心生命周期 | 可能造成状态流转或审计语义回归 | 分阶段交付，保持行为兼容测试先行 |
| 公共 API 被外部使用 | 内部拆分可能破坏第三方导入路径 | 后续设计中定义兼容导出策略 |
| 规则边界抽离不彻底 | 形成新旧职责双轨，增加理解成本 | 每个交付阶段必须包含职责边界检查 |
| 只读快照引入后数据过期 | 诊断和变更操作混用时可能读到旧状态 | 明确快照仅用于单次只读判断，写操作后重新构建 |
